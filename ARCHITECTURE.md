# Архитектура PARFUM PLACE

## Подход

Предлагается модульный монолит на PHP 8.2+: сервер формирует HTML,
CSS отвечает за оформление, JavaScript постепенно дополняет интерфейс.
Это позволяет начать с небольшой системы и развивать каталог, корзину
и оформление заказа в одном приложении. Первая витрина реализована без фреймворка и внешних зависимостей.

Поток запроса: веб-сервер → будущая точка входа `public/index.php` →
маршрутизатор → HTTP-обработчик → сценарий приложения → интерфейс
репозитория → адаптер MySQL/MariaDB → HTML-шаблон или JSON-ответ.
Первая реализация: `public/index.php` обрабатывает GET/HEAD и выводит шаблон;
`CatalogRepository` читает фактические таблицы через PDO. Выделение контроллеров
и сценариев в отдельные классы предусмотрено при добавлении корзины и заказов.

## Слои и границы

- `app/Http`: контроллеры, разбор и валидация запросов, middleware.
- `app/Application`: сценарии поиска, просмотра каталога, корзины и заказа;
  координация операций и границы транзакций.
- `app/Domain`: правила предметной области и интерфейсы репозиториев.
  Этот слой не зависит от HTTP и SQL.
- `app/Infrastructure`: реализации доступа к данным, почте, оплате и доставке.
- `resources/views`: шаблоны с экранированием данных по контексту вывода.
- `routes`, `config`, `bootstrap`: маршруты, конфигурация и сборка компонентов.
- `tests/Unit`, `tests/Integration`, `tests/Feature`: проверки правил,
  адаптеров и пользовательских сценариев соответственно.

Возможные функциональные модули: каталог и бренды, поиск и фильтры,
корзина, заказы, оплата, доставка, администрирование. Это функциональные
границы, а не перечень сущностей или таблиц существующей базы.

## Существующие данные

Существующая MySQL-база является исходным источником каталога, брендов,
ароматов, цен, объёмов и описаний. Дамп от 01.11.2026 изучен: `brands` → `products` → `product_prices`.
Фактическая схема трёх таблиц сохранена в `bootstrap/catalog_schema.php`
исключительно для новой локальной базы. Миграции исходной базы не выполнялись.
Подробности и ограничения: [анализ БД](docs/DATABASE_ANALYSIS.md).

Порядок работы с данными:

1. Проверить наличие чувствительных данных, SQL-команд с побочными эффектами,
   кодировки, collation и совместимость с целевой версией MySQL/MariaDB.
2. Импортировать проверенную копию в изолированную локальную базу;
   не использовать боевые реквизиты.
3. Документировать фактические связи, типы и правила интерпретации цен,
   валюты, вариантов объёма, доступности и описаний.
4. Реализовать адаптеры и явное сопоставление полей с моделью приложения.
   Для первичного изучения и чтения использовать учётную запись с правами
   только на чтение локальной копии.
5. Отдельно согласовать хранение корзин, заказов и клиентов, если его нет
   в существующей схеме. Любое изменение схемы — отдельная задача
   с проверкой совместимости и планом отката.

Цены и наличие при оформлении заказа проверяются на сервере. Денежные
расчёты не должны использовать двоичный float; точное представление
определяется после анализа типов и правил существующих данных.

## Безопасность

Document root — только `public/`; секреты и рабочие файлы находятся вне него.
Реквизиты берутся из окружения, не из Git. SQL выполняется через PDO
с параметризованными запросами; динамические поля сортировки выбираются
по разрешённому списку. Нужны серверная валидация, CSRF-защита изменяющих
запросов, защита от XSS, ограничение частоты чувствительных операций,
проверка прав и безопасные cookie сессии (`HttpOnly`, `Secure` при HTTPS,
`SameSite`). Пароли при появлении аккаунтов хешируются штатными средствами PHP.

Загрузки хранятся в `storage/uploads`, проверяются по размеру и содержимому;
выполнение загруженных файлов запрещено. Публикация файлов возможна только
через контролируемую выдачу. Логи не должны содержать секреты и персональные
данные. Администрирование требует отдельной проверки прав.

Платёжные данные карт не хранятся в приложении: предполагается платёжный
провайдер с проверкой подписи уведомлений и идемпотентной обработкой.
Обработка персональных данных, условия продажи и требования для рынка России
подлежат отдельному согласованию перед запуском.

## Эксплуатация и проверки

Для разработки используются локальные сервисы и тестовые интеграции.
Перед публикацией потребуются HTTPS, настройки PHP-FPM и веб-сервера,
отключение публичного вывода ошибок, закрытое журналирование, резервное
копирование с проверкой восстановления и мониторинг.

Модульные тесты проверят предметные правила; интеграционные — адаптеры
на локальной базе с фактической схемой; функциональные — каталог, корзину
и оформление заказа. Тесты не должны обращаться к боевой базе.

## Правило ассортимента

PARFUM PLACE продаёт только целые заводские флаконы. Пробники и отливанты
исключены. В текущих данных для витрины разрешены 70, 75, 90, 100 мл;
5 и 10 мл не показываются и не участвуют в расчёте минимальной цены.
При разработке корзины и заказов то же правило должно проверяться сервером.
